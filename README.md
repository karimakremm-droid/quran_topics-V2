# إصلاحات هذه الجولة: زر الرجوع، موضع البطاقة، فتح دورار في تبويبة، ورفع GitHub

## 1. زر الرجوع في قسم الأحاديث — لم يعد يخرج من التطبيق مباشرة

**السبب الحقيقي:** تطبيقك يستهدف Android 16 (API 36). الأنظمة الحديثة (Android 13+) تتعامل
مع زر/إيماءة الرجوع بآلية جديدة (Predictive Back)، والاعتماد فقط على تجاوز الدالة القديمة
`onBackPressed()` لم يعد **مضموناً** أن يُستدعى قبل أن يقفز النظام مباشرة لسلوك الخروج
الافتراضي — بالضبط العرَض الذي وصفته.

**الحل (الطريقة الحديثة الموصى بها رسمياً من جوجل):**
- أضفت `android:enableOnBackInvokedCallback="true"` في `AndroidManifest.xml`
- استبدلت `onBackPressed()` بـ `OnBackPressedCallback` مسجَّلة عبر
  `getOnBackPressedDispatcher()` في `MainActivity.java` — هذه الآلية **مضمونة الاستدعاء**
  في كل إصدارات أندرويد الحالية والمستقبلية، بعكس الطريقة القديمة
- **المنطق الداخلي (فحص لوحة الأحاديث ثم القرار) لم يتغيّر إطلاقاً** — فقط طريقة ربطه
  بالنظام هي التي أصبحت أضمن

## 2. موضع البطاقة الخضراء — انتقلت للأسفل

كانت البطاقة تُدرَج فوق "آية اليوم" مباشرة (بناءً على طلب سابق)، فتصدَّرت الواجهة قبل
المسابقة الأسبوعية والآيات كما لاحظت. الآن تُدرَج **بعد قسم "اختبار أسبوعي"** تحديداً (أو
بعد "آية اليوم" كخطة احتياط لو لم يوجد قسم الاختبار), فتظهر متأخرة في التمرير بدل منافسة
محتوى التطبيق الأساسي على الصدارة، مع بقائها عنصراً ثابتاً لا يختفي كما طلبت سابقاً.

## 3. فتح "دورار السنية" في تبويبة منفصلة (الويب)

**السبب:** الدالة كانت تستخدم `window.location.href = url` في نسخة الويب (عند عدم توفّر
جسر أندرويد) — وهذا **يستبدل** الصفحة الحالية بدل فتح تبويبة جديدة، بعكس سلوك تدبر
الأصلي الذي يفتح تبويبة منفصلة فعلاً.

**الحل:** استبدلتها بـ`window.open(url, "_blank", "noopener")` — يفتح تبويبة جديدة تماماً
كموقع تدبر، ويحافظ على تطبيقك مفتوحاً في تبويبته الأصلية دون فقدان مكانك فيه. هذا الحل
**موحّد لكل من الحاسوب وiOS وأندرويد** على المتصفح (وليس التطبيق الأصلي) — الأنسب فعلياً
لكل المنصات لأنه يحافظ على حالة التطبيق دون الحاجة لأزرار "رجوع" متعددة.

**ملاحظة:** هذا يخص نسخة الويب فقط. نسخة أندرويد الأصلية (APK) تفتح الشرح دوماً داخل
نافذة التطبيق نفسه (كما بنيناها سابقاً)، ولم تتأثر بهذا التغيير.

## 4. مشكلة "Commit failed... file too large" على GitHub — السبب والحل الصحيح

**التشخيص:** فحصت كل الملفات الفردية — **لا يوجد ملف واحد يتجاوز 8.4MB** (أكبرها
`hadiths.dat`)، فالمشكلة ليست في حجم أي ملف بيانات. المشكلة أن **الملف المضغوط (zip) الذي
ترفعه كاملاً كملف واحد** يتجاوز 25MB — وهو حد الرفع المباشر عبر واجهة GitHub بالمتصفح
(Drag & Drop / Add file).

**نقطة أهم:** GitHub Pages **لا يعمل من ملف zip موجود في المستودع أصلاً** — يحتاج الملفات
مستخرجة فعلياً كشجرة ملفات عادية في المستودع (`index.html`، `app.enc`، `data/`، `assets/`
كملفات ومجلدات حقيقية، وليس مضغوطة).

**الحل الصحيح (يُنهي المشكلتين معاً):**
1. فك ضغط `github_pages_final3.zip` (المرفق هنا) على جهازك
2. استخدم Git من سطر الأوامر بدل واجهة الرفع بالمتصفح:
   ```
   git clone https://github.com/karimakremm-droid/tiwikirosta99.git
   cd tiwikirosta99
   # احذف أي ملفات/مجلدات قديمة إن وُجدت، ثم انسخ محتويات الزيب المستخرَج هنا
   git add .
   git commit -m "تحديث: قسم الأحاديث + إصلاحات"
   git push
   ```
   Git من سطر الأوامر يدعم رفع ملفات حتى 100MB بدون أي مشكلة (بعكس واجهة المتصفح المحدودة
   بـ25MB) — وهذه الطريقة الصحيحة والوحيدة لنشر GitHub Pages أصلاً.
3. إن لم يكن لديك Git مثبَّتاً، أبسط بديل: على صفحة المستودع في GitHub، احذف أي ملف zip
   قديم موجود، ثم استخدم "Add file → Upload files" **لكل ملف/مجلد على حدة** بدل رفع الزيب
   كاملاً دفعة واحدة (كل ملف هنا أصغر من 25MB بمفرده، فسينجح الرفع).
